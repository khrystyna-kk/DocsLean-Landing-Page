# DocsLean — Styleguide & Responsive Rules

Правила компонування і респонсив-поведінки для лендінгу DocsLean. Джерело кольорів/розмірів — `styles/tokens.css`; тут — тільки логіка layout і адаптації, стилістика (кольори, тіні, "без градієнтів") між breakpoints не змінюється.

## Підхід

**Desktop-first**: базові стилі (без media query) пишуться під desktop. Tablet і mobile — override через `max-width` media queries.

```css
/* Desktop — базовий стиль, без media query */
.hero { display: flex; }

/* Tablet override */
@media (max-width: 1024px) { ... }

/* Mobile override */
@media (max-width: 640px) { ... }
```

Breakpoints (з `styles/tokens.css`):
- **mobile**: до 640px
- **tablet**: 641–1024px
- **desktop**: 1025px+ (базовий рівень стилів)

## Навбар

- **Desktop**: sticky. Прозорий на hero → після скролу за межі hero перемикається клас `.scrolled` (світлий фон + темний текст).
- **Tablet/mobile**: якорі («Як це працює», «Що змінюється», «Продукт», «FAQ») ховаються в burger-меню. Лишається тільки лого + іконка бургера. CTA-кнопки в навбарі немає на жодному розмірі (це узгоджено в ТЗ).

## Hero

- **Desktop**: layered mockup cluster (2 накладені картки-тизери) — збоку, асиметрично відносно тексту (не під заголовком по центру).
- **Mobile**: кластер переміщується під текст, картки йдуть вертикальним стеком; якщо дві картки не вміщаються без втрати читабельності — лишити тільки одну (передню, з health score).

## «Як це працює» (3 кроки)

- Заголовок кожного кроку — **завжди в один рядок** (`white-space: nowrap`), картка досить широка під найдовший заголовок. Текст-опис під заголовками тримати приблизно однакової довжини символів (±10%) між усіма кроками, щоб вони переносились в однакову кількість рядків — інакше картки виглядають різної висоти навіть при однаковій ширині.
- **Desktop**: 3 колонки в ряд.
- **Tablet**: 2 колонки + 1 знизу, або 3 вузькі колонки в ряд — обирати за тим, що не ламає читабельність тексту кроку.
- **Mobile**: 1 колонка, кроки вертикально один під одним по порядку 1→2→3.

## «Що змінюється» (Before/After + stat-рядок)

- **Desktop**: 2 колонки поруч; під ними stat-рядок — 3 числа в один ряд.
- **Mobile**: колонки — вертикальний стек; stat-рядок — вертикально або 2+1 (два числа в ряд, третє під ними).

## Deep-dive (dashboard-скрін)

- **Desktop**: повний детальний скрін, як спроєктовано.
- **Mobile**: скрін масштабується по ширині контейнера зі збереженням пропорцій (`max-width: 100%; height: auto`); якщо всередині скріна є широкі таблиці/елементи, що не стискаються — горизонтальний скрол лише для цього внутрішнього блока, не для всієї секції.

## CTA + FAQ

Однаково добре працює на всіх розмірах — просто звужується по ширині контейнера. Логіка accordion (miттєвий toggle, без анімації розгортання) не змінюється між breakpoints.

## Футер

- **Desktop**: два блоки, не чотири рівновіддалені елементи — лого+тег-фраза утворюють одну групу (щільний gap, це один "фрейм"), копірайт+email іншу; блоки розведені по краях (`justify-content: space-between`).
- **Mobile**: обидва блоки — вертикальний стек по центру.

## Заголовки секцій

- Усі `<h2>` секцій, крім hero і футера, **центруються** по горизонталі (текст + сам блок).
- On-page заголовок секції — це не те саме, що коротка навбар-якір-мітка («How it works», «What changes» тощо лишаються короткими тільки в навбарі). Сам `<h2>` на сторінці має бути повноцінним реченням/фразою (орієнтовно 7–13 слів), а не дослівним повторенням 2–5-слівної навбар-мітки.

## Типографіка на менших екранах

Масштабується тільки великий рівень (h1–h3); `caption`/`body-sm`/`body`/`subheading` лишаються незмінними на всіх breakpoints (нижче 14–16px текст стає нечитабельним). Чим більший desktop-розмір заголовка — тим сильніше він стискається на mobile (є запас); h3 вже близький до subheading, тому зменшується мінімально, щоб не загубити ієрархію рівнів. Точні значення — в `styles/tokens.css`:

| | Desktop | Tablet | Mobile | Δ до mobile |
|---|---|---|---|---|
| `--font-size-h1` | 56px | 44px | 36px | −36% |
| `--font-size-h2` | 32px | 28px | 22px | −31% |
| `--font-size-h3` | 24px | 21px | 19px | −21% |

Пропорції зберігаються — **не скидати** `line-height`/`letter-spacing` до дефолтних браузерних значень. Обидва задані в em/unitless, тому масштабуються разом з розміром автоматично — окремих override для них не потрібно.

**Довжина рядка**: максимум **45–60 символів** на рядок для body/subheading-тексту (жорсткіше за загальноприйняті ~75) — обмежувати через `max-width` на контейнері тексту, а не сподіватись, що це вийде саме собою. `text-wrap: balance` на заголовках і `text-wrap: pretty` на параграфах/списках — щоб не лишалось «сирітських» слів на останньому рядку.

## Загальні правила

- **Відступи**: на будь-якому breakpoint — тільки значення зі шкали `--space-1`…`--space-9` (8/16/24/32/40/48/64/80/96px). На менших екранах брати менші токени з тієї ж шкали (наприклад, замінити `--space-9` на `--space-4` між секціями), ніколи довільні пікселі поза шкалою.
- **Border-radius**: `--radius-base: 8px` незмінний на всіх розмірах екрана, без винятків (крім pill-бейджів — `--radius-pill`, теж незмінний).
- **Кольори, тіні, відсутність градієнтів**: не змінюються між breakpoints. Адаптується тільки layout (кількість колонок, напрямок flex, видимість елементів), ніколи стилістика.
- **Просторова ієрархія (proximity)** — стосується всього лендінгу, не тільки hero: якщо два елементи візуально споріднені (заголовок+підзаголовок, підзаголовок+список), відступ між ними має бути ЯВНО менший, ніж відступ до наступного, самостійного елемента (кнопки, картки, наступної групи). Приклад з hero: заголовок→підзаголовок = `--space-2` (16px), підзаголовок→CTA = `--space-6` (48px). Не покладатись на "має вийти само" — різниця має бути навмисною і помітною.
- **Рівновисокі поля в порівняльних блоках** (типу Before/After): якщо картки стоять рядами одна навпроти одної — верстати їх як прямі grid-комірки одного grid-контейнера (рядок = обидві картки), а не як два незалежні `<ul>` в сусідніх колонках — тоді висота вирівнюється сама через `align-items: stretch` замість підганяння вручну.
- **Score-кольори як текст vs заливка**: `--color-score-warning` (`#F97316`) і `--color-score-good` (`#16A34A`) не проходять WCAG AA як колір ЗВИЧАЙНОГО ТЕКСТУ на світлому фоні (2.8:1 і 3.3:1) — використовувати їх тільки для заливок/бейджів/іконок. Якщо потрібен саме кольоровий текст (наприклад підпис "+12% цього тижня") — брати `--color-score-warning-text` (`#C2410C`) / `--color-score-good-text` (`#15803D`), обидва проходять 4.5:1. `--color-score-critical` (`#DC2626`) проходить і як текст (4.8:1), окремого варіанту не потребує.
